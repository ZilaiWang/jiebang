# Day2 · 4号 评委视角验收清单（OpenCode 调度证据）

> 用途：2号 的 ledger 出来后，4号 站在评委角度逐项打勾。
> 依据：赛题 XH-202630 评分标准（完整性30 / 创新性25 / 体验15 / 实用价值30）。
> 核心问题：**评委看这份调度证据，能不能相信"这是多智能体协同决策系统，而不是前端顺序调 API 的壳"？**

## A. 作品完整性（30分）——协同闭环可见性

| # | 检查项 | 评委要能看到 | 结果 |
|---|---|---|---|
| A1 | 分析环节可见 | "学情诊断 Agent"出题、收答案、判定，有输入输出记录 | ☐ |
| A2 | 生成环节可见 | 领域知识生成（讲义/代码实验/测评）对应真实 Agent 调用 | ☐ |
| A3 | 校验环节可见 | 审核 Agent 独立存在，能看到审核结论（通过/驳回） | ☐ |
| A4 | 决策环节可见 | 测评后能看到 remediate/reinforce/advance/reprofile 决策及理由 | ☐ |
| A5 | 闭环顺序完整 | 能按时间线看出 分析→生成→校验→决策 完整循环 | ☐ |
| A6 | ≥3个职责明确Agent | 至少学情诊断、内容生成、内容审核3类，职责描述清楚 | ☐ |

## B. 技术创新性（25分）——不是 API 堆叠

| # | 检查项 | 评委要能看到 | 结果 |
|---|---|---|---|
| B1 | 主 Agent 是调度者 | 主 Agent 只调度不代做业务（生成内容来自子 Agent） | ☐ |
| B2 | 交叉验证/辩论痕迹 | 审核 Agent 对生成内容有独立复核动作，不是走过场 | ☐ |
| B3 | 失败/重试/纠偏可见 | 有 Agent 失败→重试→修复或降级的记录（防幻觉证据） | ☐ |
| B4 | 知识溯源可见 | 生成内容能指回 source_id/fact_id（高保真证据） | ☐ |
| B5 | 不是"顺序调API" | 能区分：会话逻辑/固定程序适配/审核流水线 ≠ OpenCode 子 Agent | ☐ |
| B6 | 个性化差异可见 | 不同学习者调用链/资源有差异，不是千人一面 | ☐ |

## C. 用户体验（15分）——评委看得懂

| # | 检查项 | 评委要能看到 | 结果 |
|---|---|---|---|
| C1 | 主 Agent 是谁 | 一眼看出调度主脑是 learning-orchestrator | ☐ |
| C2 | 子 Agent 名单 | 有哪些 Agent、各干什么，中文说明清楚 | ☐ |
| C3 | 调用顺序 | 谁先谁后、是否跳步，时间线清晰 | ☐ |
| C4 | 产物引用 | 每个 Agent 的输出指向哪个真实文件/ID | ☐ |
| C5 | 术语可读性 | envelope/input_refs/output_refs 等有中文解释或注释 | ☐ |
| C6 | 状态可视化 | 前端或文档能看到"正在运行/已完成/失败"状态 | ☐ |

## D. 实用价值（30分）——证据能支撑指标

| # | 检查项 | 评委要能看到 | 结果 |
|---|---|---|---|
| D1 | 调度数据可复现 | 用 ledger 能重跑/复现一次真实调度 | ☐ |
| D2 | 可支撑样例 | ≥3组学习者各自有调度记录可查 | ☐ |
| D3 | 可支撑指标 | 幻觉率/难度适配/覆盖率统计能对应到具体运行记录 | ☐ |
| D4 | 可迁移 | 调度框架不绑死单一领域，能说明可换知识库复用 | ☐ |

## E. 硬性红线（一票否决）

| # | 检查项 | 结果 |
|---|---|---|
| E1 | 无 API Key / 本机路径 / 私有判题答案泄露 | ☐ |
| E2 | 没有把"代码中存在的能力"写成"本次运行已发生"（2号 P1 教训） | ☐ |
| E3 | 没有用第二轮产物 ID 冒充第一轮（2号 P4 教训） | ☐ |
| E4 | 没有把固定程序适配/会话逻辑统称为"子 Agent" | ☐ |
